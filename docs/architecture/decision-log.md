# Decision Log

All decisions taken during refinement and design (2026-10-28). Each one was approved by a human. "Origin" shows who proposed it: **Human** (the developer), **AI** (proposed by the assistant and approved), or **Human over AI** (the developer chose differently from the AI recommendation).

## Domain and API

| ID | Decision | Alternatives considered | Rationale | Origin |
|---|---|---|---|---|
| D01 | Events enter through `POST /events`, are stored and matched against active subscriptions. | Seed only; real broker consumer. | Controllable demo; a Kafka consumer adapter is a documented evolution. | Human |
| D02 | `notification_events.json` is seed data for querying, not the ingestion mechanism. | Treat records as pending deliveries. | Keeps the original state; failed records are immediate replay candidates. | Human |
| D03 | Add `created_at` (filter field). `delivery_date` = final outcome of the current round; `delivered_at` = first 2xx. | `delivery_date` = first 2xx, transforming the sample. | Keeps the sample unchanged and matches "storing the final information related to the delivery". | AI |
| D04 | One notification event per matching subscription (1:N). | One notification per event (1:1). | More realistic; replay targets one destination. | Human over AI |
| D05 | `failed` = permanent error or exhausted retries; only transient errors are retried. | — | Direct reading of "definitely failed". | Human |
| D06 | Replay is asynchronous (`202`), only from `failed`, keeps ID and history, starts a new round of up to 5 attempts. | Synchronous replay. | Delivery may take minutes; the API must not block. | Human |
| D07 | `POST /events` with an existing `event_id` returns `409 Conflict` and creates no notifications. Producers treat `409` as "already accepted". | `200` with the original result. | Explicit signal of a duplicate. | Human over AI |
| D08 | Offset pagination, default 20, maximum 100. | Cursor (keyset) pagination. | Simpler; the cap limits cost. Keyset is a documented evolution. | AI |
| D09 | New IDs are UUIDv7; seeded records keep `EVT001`… | UUIDv4. | Time-ordered IDs keep index locality. | AI |
| D10 | JSON in `snake_case`; errors as RFC 9457 `application/problem+json`; timestamps ISO-8601 UTC. | camelCase; custom error body. | Matches the sample and the `/notification_events` path; standard error format. | AI |

## Messaging and delivery

| ID | Decision | Alternatives considered | Rationale | Origin |
|---|---|---|---|---|
| D14 | Kafka for dispatch, retry topics and dead-letter topic; PostgreSQL as source of truth with a transactional outbox. | RabbitMQ; SQS on LocalStack; PostgreSQL-only queue. | Aligns with the stack Cobre publishes in job postings (secondary source, not confirmed by Cobre). The outbox avoids the dual-write problem. | Human over AI |
| D15 | Outbox relay polls with `SELECT … FOR UPDATE SKIP LOCKED`. | Debezium CDC. | No extra infrastructure; safe with several replicas. Debezium is the evolution. | AI |
| D16 | Kafka partition key = `notification_event_id`; no ordering guarantee (documented). | `subscription_id` (per-destination order). | Even load; a slow client cannot block others on its partition. | AI |
| D17 | Non-blocking retries with `@RetryableTopic` (implemented with `RetryTopicConfigurationBuilder`, its programmatic form, in `DispatchRetryConfiguration`); the dead-letter handler marks the notification event `failed`. Replay starts from the database, never from the dead-letter topic. Superseded in part by D70: the last attempt fails the event; the dead-letter handler is a fallback. | Blocking retries. | One unhealthy receiver does not delay others. | AI |
| D18 | 5 attempts per round, exponential backoff with jitter, per profile (demo: 0 s, 10 s, 30 s, 1 min, 2 min). | Fixed delays. | Visible in a live demo; realistic in production profile. | AI |
| D19 | Retried: timeouts, connection errors, `5xx`, `408`, `429` (honoring a capped `Retry-After`; the cap is set by D49). Immediate `failed`: other `4xx`, TLS or certificate errors, SSRF-blocked destinations. | Retry everything. | Retrying permanent errors wastes capacity. | AI |
| D20 | HTTP timeouts: connect 2 s, read 5 s, total 10 s. The read timeout is removed and the total limit is set by D50. | Library defaults. | A slow receiver must not hold consumer threads. | AI |
| D21 | The domain classifies outcomes (`SUCCESS`, `RETRYABLE`, `PERMANENT`); the Kafka adapter only maps them to retry or no retry. | Retry rules inside Kafka configuration. | Business rules survive a broker change (fallback plan). | AI |

## Security

| ID | Decision | Alternatives considered | Rationale | Origin |
|---|---|---|---|---|
| D22 | One mechanism (JWT, OAuth2 Resource Server, RS256) with separate scopes and audience: clients get `notifications:read`/`notifications:replay`, `subscriptions:read`/`subscriptions:write` and a `client_id` claim; producers get `events:write` and an internal audience. A client token on `POST /events` returns `403`. | mTLS for producers; static API key. | Simple, testable; mTLS is the production evolution. | AI |
| D23 | Locally, tokens come from a development-only tool; Keycloak or Cognito is the production issuer. | Keycloak in Docker Compose. | Less infrastructure that can fail during the demo. | AI |
| D24 | Webhooks signed with HMAC-SHA256: `Cobre-Signature: t=<ts>,v1=<hex>` over `t + "." + body`, 5-minute tolerance, plus `Cobre-Notification-Id` for deduplication. | HTTPS only, HMAC as future work. | Lets receivers verify the sender; low cost. The developer first left HMAC out of the MVP and accepted it after the trade-off was discussed. | AI |
| D25 | Per-subscription secret, shown once, encrypted at rest with AES-GCM (key from environment). | Plain text with documented risk. | HMAC needs the secret in clear to sign, so hashing is not possible. | AI |
| D26 | SSRF: HTTPS only, host allowlist by environment variable, validation at registration and at send time, IP pinning against DNS rebinding, private/loopback/link-local blocked, no redirects, URL never taken from events. | Allow one fixed URL. | Works with per-subscription URLs and the presentation host. | AI |
| D27 | OWASP API Security Top 10 (2023) as primary reference. API1, API2 and API7 are implemented and tested; API3, API4 and API8 are documented. | OWASP Top 10 (2021) only. | The project exposes an API. | AI |
| D28 | Structured audit log for replays and subscription changes. | Audit table. | Cheap and enough for the scope. | AI |
| D29 | Per-client rate limiting with Bucket4j in memory (Could); Redis as evolution. | Documented only. | Mitigates API4 if time allows. | AI |
| D30 | Vulnerable transitive dependencies are pinned with Gradle constraints to the latest patch release of the same line, with the advisory in `because(...)`. Constraints are removed when the upstream library ships a fix. | Upgrade to a new minor version. | Smallest change that fixes the vulnerability. | AI |

| D37 | All documentation in English. The initial prompt is kept verbatim in Spanish as evidence. | Spanish docs. | Consistent artifacts; evidence must not be altered. | Human |
| D38 | OpenSpec specs follow the five capabilities of the challenge plan. | Seven finer-grained specs. | Direct traceability to the plan. | AI |
| D39 | Branches: `main` and `develop`; one feature branch per OpenSpec change, from `develop`; squash merge into `develop`; merge commit from `develop` into `main`; feature branch deleted after merge. | GitHub Flow without `develop`. | Developer's choice. | Human |
| D40 | Conventional Commits, no AI attribution; the developer reviews every diff before it is committed. | — | Developer's rule. | Human |
| D41 | Test-first at scenario level: every Given/When/Then scenario becomes a test before implementation. | Strict class-level TDD. | Fits two days; no scenario is left untested. | AI |
| D42 | Unit tests for the domain; Testcontainers (PostgreSQL, Kafka) and WireMock over HTTPS for adapters; acceptance tests from OpenSpec scenarios. | — | Each layer tested with the right tool. | AI |
| D43 | CI on every pull request: OpenSpec validation (`--strict`), Gradle build with tests, dependency graph submission and dependency review (fails on high severity). | Build only. | Quality does not depend on anyone's word. | Human + AI |
| D44 | Implementation in the main session; a fresh-context AI reviewer audits each change before its pull request; dual blind review for the delivery and security change. | Delegate implementation to sub-agents. | All design context lives in the main session; the reviewer's value is independence. | AI |
| D45 | Parallel work in separate sessions and Git worktrees: implementation critical path (changes 1 → 2 → 3) in the main session; documentation and presentation in a parallel session; subscription management (change 4) in parallel once change 1 is merged. At most three fronts at once. | One session for everything. | Human review is the bottleneck, not the AI. | AI |
| D46 | Flyway migration numbers reserved per change: V1 query schema, V2 ingestion and outbox, V3 subscription management, V4 replay, V5 observability and audit. Change 4 needed no schema change; V3 is now used by `V3__add_processing_lease.sql` (#20). Superseded by D65. | First come, first served. | Parallel branches do not collide. | AI |
| D47 | The `add-self-service-query` specs are approved for implementation. | — | SDD human gate. | Human |
| D48 | The panel deliverable is a slide deck. | Written document. | The statement allows either format; developer's choice. | Human |
| D49 | `Retry-After` on `429` and `503` is honoured up to a cap of 300 seconds, configurable per environment. A value above the cap schedules the retry at the cap, never earlier. A missing or invalid value uses the configured backoff. Supersedes the unspecified cap in D19. | Honour `Retry-After` without a cap; ignore it. | A receiver cannot stall a delivery indefinitely, and the five-attempt limit per round still applies. | Human + AI |
| D50 | Each delivery attempt has a total limit of 10 seconds, enforced by cancelling the request, so a slow receiver cannot hold a worker. The separate 5-second read timeout in D20 is removed. Supersedes the read timeout in D20. | Separate 5-second read timeout; library defaults. | The total limit is the guarantee the design needs. The JDK behaviour must be verified before implementation. | Human + AI |
| D51 | A client has at most 50 active subscriptions. Creating or reactivating one past the limit returns `409 Conflict` as problem+json with `code: SUBSCRIPTION_LIMIT_REACHED`. The check is atomic, so concurrent requests cannot exceed the limit. Patching an already active subscription is never refused. Records reconciliation decision 3. | Check on creation only; `422`. | Bounds resource use per client (OWASP API4, D27). | Human + AI |
| D52 | Subscription bounds: 1 to 50 event types, each matching `^[a-z0-9_]{1,100}$`; destinations on port 443 only, which tightens D26. `GET /subscriptions` returns the 100 newest subscriptions without pagination, inside a `{"data": [...]}` envelope. | Offset pagination as in D08; any port. | Active subscriptions are capped at 50, so the list rarely exceeds 100. The envelope allows adding a cursor later without breaking the contract. | Human + AI |
| D53 | A valid `Retry-After` below the cap of D49 is used exactly: it replaces the backoff step for that attempt. `Retry-After: 0` uses the configured backoff step. Supersedes the "0 to 300 seconds is honoured" clause of reconciliation decision 4a. | The larger of the value and the backoff step; `0` as an immediate retry. | Follows the receiver's request (RFC 9110). An immediate retry would add load to a receiver that just said it is overloaded. | Human + AI |
| D54 | A DNS resolution failure at send time is retryable, whatever its cause (NXDOMAIN, SERVFAIL or timeout). A host that resolves to a non-public address stays an immediate `failed` (D19, D26). Validation at registration is unchanged. | Separate NXDOMAIN (permanent) from transient failures; keep every DNS failure permanent. | The JDK resolver reports every cause as the same `UnknownHostException`; telling them apart needs a DNS library. The limit of 5 attempts per round bounds the cost of a real NXDOMAIN. | Human + AI |
| D55 | Delivery is at-least-once while the configured attempts and recovery operations run. A webhook may reach the receiver more than once, and receivers deduplicate with `Cobre-Notification-Id`. A timeout does not prove that the receiver did not process the request. There is no end-to-end exactly-once guarantee. Records reconciliation decision 6. | Claim exactly-once. | Exactly-once over HTTP to a third party is not achievable. | Human + AI |
| D56 | Processing recovery uses a lease, an atomic claim and a generation (fencing) token; every write of an attempt is conditional on the token. The lease lasts 60 seconds and a recovery sweep runs every 30 seconds, both configurable. The lease lives in internal columns (`lease_expires_at`, `generation`); the public `delivery_status` values do not change. An interrupted attempt is recorded with `error_type` `interrupted` and counts toward the 5 attempts of the round; it is never recorded as a receiver failure. Records reconciliation decision 7. | A lease of 30 seconds with a sweep every 10 seconds; a public `processing` status; interrupted attempts not counted, with a separate recovery limit. | The lease is six times the 10-second attempt limit of D50. Counting interrupted attempts stops a crashing worker from looping forever. | Human + AI |
| D57 | Replaying a notification event whose subscription is now inactive is allowed. The replay goes to the destination snapshot (D13), signs with that subscription's secret and validates the destination again at send time. | Reject with `409`. | The client asked for this replay explicitly; reactivating the subscription would also resume new deliveries. | Human + AI |
| D58 | The application `Clock` is the source of truth for domain and API timestamps (`created_at`, `delivery_date`, `delivered_at`, attempts, leases), which are passed to SQL as parameters. PostgreSQL `now()` is allowed only in technical columns such as `outbox.published_at`. | PostgreSQL `now()` everywhere; no rule. | One clock avoids skew between replicas and the database when timestamps are compared (for example lease expiry), and keeps tests deterministic. | Human + AI |
| D59 | `ClientId` is a shared kernel, `com.cobre.notifications.kernel.domain`, used by subscriptions and notification events. The two capabilities no longer hold separate copies. | Keep one copy per capability; a shared `shared.*` package. | One identity type avoids drift; `kernel` is outside `shared` so the hexagonal test still forbids framework imports in the inner layers. | AI, pending human approval |
| D60 | Superseded by D58 (develop). One `Clock` bean in `shared.config`; every capability receives it. Nothing calls `Clock.systemUTC()` except that bean. | Inline `Clock.systemUTC()` per configuration. | Tests can replace the clock in one place; behaviour does not change in production. | AI, pending human approval |
| D61 | Superseded by D51 (develop). Reactivating a subscription counts against the 50-active limit, the same as creating one. Patching an already active subscription is never rejected for the limit. | Limit on create only (the previous behaviour). | Closes a bypass of OWASP API4; the limit is about active subscriptions, not about writes. | AI, pending human approval |
| D62 | Superseded by D57 and D67. An inactive subscription stops new deliveries. The consumer checks the subscription state in the database before each attempt, never from the Kafka message, and replay is refused with `409 Conflict` while the subscription is inactive. A notification whose subscription is inactive at send time ends `failed` with `error_type = subscription_inactive`, with no request sent and no retry. Reactivation does not resend cancelled notifications; that needs an explicit replay with the subscription active. Delivered notifications keep their success. The schema is unchanged. Residual race: a deactivation that happens after an HTTP request has started cannot stop that request. This is documented and covered by a test. An improvement, a `cancelled` status, needs a migration and is left for later. | A `cancelled` status (new migration, API enum change); check only on create. | Keeps the behaviour the challenge needs without a migration, and avoids conflicts with the recovery change. | Human + AI; implementation waits for the recovery branch |
| D63 | A delay requested with `Retry-After` is applied through PostgreSQL: the attempt stores `next_attempt_at`, and a scheduler republishes due attempts through the outbox. The fixed-delay retry topics of D17 keep handling backoff steps. | A not-before timestamp in the message, re-delayed by the consumer; one delay topic per bucket. | Exact delays (D53), survives restarts and never pauses a partition (D16). | Human + AI |
| D64 | Every attempt of a notification event, in every round including replays, sends a byte-identical body, so receivers can compare bodies under the same `Cobre-Notification-Id`. | Identical only within a round. | Makes deduplication and signature checks predictable for receivers. | Human + AI |
| D65 | Flyway versions follow the order of implementation: the next migration takes the next free number. Supersedes the per-change reservation of D46, which no longer matches the repository. | Keep the D46 reservations. | A gapless sequence is easier to read; changes now land in sequence. | Human + AI |
| D66 | A DNS resolution failure at send time is recorded with `error_type` `dns_error`, separate from `connection_error` and `invalid_destination`. | Reuse `connection_error`. | Attempt history and metrics show the real cause. | Human + AI |
| D67 | Deactivating a subscription only stops matching new events. Notification events that already exist keep their delivery and retries, and inactivity alone never blocks an attempt or a replay (D57). A subscription without a secret is never delivered unsigned: the attempt fails permanently with `error_type` `missing_secret` and no request is sent. Supersedes D62. | Stop deliveries and refuse replays of inactive subscriptions (D62). | Deactivation is not a retroactive cancellation; an explicit replay is the client's choice. | Human + AI |
| D68 | A `Retry-After` is scheduled with `next_attempt_at`, a persisted instant on the notification: the publisher does not send the attempt before it, including after a restart. This is a documented exception to D58, limited to `next_attempt_at`: it is a technical scheduling column, computed and compared with PostgreSQL `now()`, never with one clock for one and another for the other. Leases and domain timestamps keep the application clock (D56, D58). This is not a general permission to use `now()` in domain logic. Table: a valid value up to the cap of D49 (300 s) is used exactly (D53); `0` uses the configured backoff step; an HTTP date in the past uses the backoff step; a missing or invalid value uses the backoff step; a value above the cap uses the cap of D49. | A not-before timestamp computed with the application clock; an in-memory delay. | A persisted instant survives restarts (D63). Computing and comparing with one clock avoids skew between the time written and the time checked. | Human + AI |
| D69 | A name lookup that does not finish within the resolve timeout (5 seconds) is a resolution failure recorded as `dns_error`, like a name that does not resolve (D54, D66). An unexpected resolver error is recorded the same way. | Fail the attempt as `connection_error` or `timeout`. | A slow resolver is not a slow receiver: the round retries it, and the attempt history shows the real cause. | Human + AI |
| D70 | The last retryable attempt of a round fails the notification event in the same write as the attempt: `delivery_date` is set, `last_error` keeps the attempt's error type, and no next attempt is scheduled (a `Retry-After` on that attempt is ignored). Its message is then sent straight to the dead-letter topic, not retried, so the `cobre-dead-letter` alert and metric keep counting it. The dead-letter handler counts every message and fails only events that are still open, as a fallback. Supersedes the part of D17 that says the dead-letter handler marks the event `failed`. | Keep failing in the dead-letter handler: the event stays `retrying` with no attempts left for up to one backoff step when Kafka hops and attempts diverge, for example after a `Retry-After`. Fail in the same write but end the message without a dead-letter: the alert would miss it. | Clients see `failed` right after the fifth attempt, never `retrying` with no attempt left, and the dead-letter alert keeps its meaning. Known gap: if the process stops after the `failed` write and before the dead-letter publish, the redelivered message is ignored because the event is final, so it never reaches the dead-letter topic; the failed-rate alert still counts it. | Human + AI |
